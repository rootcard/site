Developers

Two libraries and one HTTP binding.

The core is pure: no I/O, no clock, no randomness of its own. Rust (rootcard, rootcard-host) and JavaScript (rootcard on npm) produce the same bytes, checked against the shared vectors of the specification.

Relying party

Verify a proof

Give the user a fresh 32-byte challenge and your own recipient string. The user signs it with their account key (in their home's client) and sends you the proof and their log. Fetch the newest log from their home if you want to be sure it is current, then verify. Store at most the newest log per identity you deal with, and key your accounts by the account id: it never changes.

Signed-in users of {{home.name}} can make proofs on their account page. A proof can also sign a public statement instead of your challenge ([PRF-5]): it is replayable by design, so it should say what it is for and until when. Anyone can check either kind in the browser on the look-up page, which stamps the result on the ID card; the account page gives statements out as a link (/card#proof=…).

import { verifyProof, compareLogs } from "rootcard";

// 1. challenge = crypto.getRandomValues(new Uint8Array(32))
// 2. the user returns { proof, log }
// 3. optionally fetch the newest log from the home:
//    GET {{home.url}}/v0/id/{account}/log

const state = await verifyProof(proof, log, challenge,
  "https://shop.example",
  { realms: ["{{home.realm}}"], now: Math.floor(Date.now() / 1000) });

state.account   // the stable key for your user table
state.handle    // "Astra#3F9C", for display
Host

Run your own home

rootcard-host is a library, not a server: it owns the rules and leaves HTTP, storage and secrets to you. Implement three storage traits (identities with compare-and-swap, single-use challenges, sessions), pass your clock and random bytes, and wire http::route into any HTTP server.

This site is exactly that: an axum server with SQLite storage. Its source is a good starting point.

  • Hosts never see a password and never run Argon2id.
  • Build the core without its vault feature.
  • Serve your client pages with a strict CSP; they handle passwords.
# Cargo.toml
rootcard-host = "{{rootcard_version}}"
rootcard = { version = "{{rootcard_version}}", default-features = false }

// main.rs
use rootcard_host::{Host, HostConfig, RealmConfig, UsernamePolicy};
use rootcard_host::http::{route, Request};

let host = Host::new(HostConfig {
    key_seed,                                  // your host key
    retired_keys: vec![],
    urls: vec!["https://id.example.com".into()],
    realms: vec![RealmConfig { realm: "myapp".into(),
                               policy: UsernamePolicy::DEFAULT }],
    peers: vec![],
}, identities, challenges, sessions);

// for every request under /v0:
let res = route(&host, &Request { method, path, bearer, peer, body },
                now, &mut |b| getrandom::fill(b).unwrap());
Client

Register and sign in from the browser

The npm package has zero dependencies and no build step. rootcard is the verification core; rootcard/vault adds passwords, Argon2id and vault encryption. The flows are in the host protocol, §7. This site's pages are a complete client: registration, sign-in, profile and private data, linked accounts, password change and proofs.

Generate the recovery key in the client, make the user save the recovery card before you send the registration, then erase it. Never ask for the recovery key in an application client.

import { register } from "rootcard/vault";
import { systemRandom, newRecoveryKey, KDF_DEFAULT } from "rootcard";

const base = "{{home.url}}";
const d = await (await fetch(`${base}/v0/host`)).json();
const rk = await newRecoveryKey("{{home.realm}}", "Astra", systemRandom);
const reg = await register(rk, "{{home.realm}}", "Astra", password,
  "Password", { key: d.key, url: base },
  Math.floor(Date.now() / 1000), KDF_DEFAULT, systemRandom);
rk.fill(0);

// show and save reg.card first, then:
await fetch(`${base}/v0/id/register`, { method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ log: reg.log, vault: reg.vault,
                         public: reg.public }) });
Linked accounts

Check a user's GitHub account or domain

A public profile may list accounts elsewhere in user.links (SPEC §12.3). A link has two sides, and you check both yourself: the signed profile lists the account, and the account carries the identity's token rootcard:<account id> where only its owner can write (a GitHub bio or gist, /.well-known/rootcard-link on a website, a TXT record at _rootcard.<domain>).

The core does no I/O: linkRequests says what to fetch, you fetch it (HTTPS, no redirects, no credentials, at most 64 KiB, 10 s), and checkLink decides. The services are descriptors bundled with the packages, never loaded at run time. Signed-in users of {{home.name}} add links on their account page; the look-up page checks them in the viewer's browser, on request.

const registry = rc.registry();
const { data } = await rc.verifyPublic(profile, state);
for (const { link, status } of rc.parseLinks(data, registry)) {
  if (status !== "ok") continue;  // unsupported or bad_link
  const d = rc.findDescriptor(registry, link.service);
  const answers = await Promise.all(
    rc.linkRequests(link, d).map(fetchUnderLnk9));
  rc.checkLink(link, state.account, d, answers);
  // verified, by you, now; else wrong_owner,
  // token_missing or fetch_failed
}
{{home.name}} as a home

This home's API

There is no central rootcard API: every home serves the same binding at its own base URL. {{home.name}} serves it for the {{home.realm}} realm. Every endpoint below is under {{home.url}}/v0. The base URL that goes into logs and signed messages is {{home.url}}, without the version.

GET /hostHost key, addresses and realms120 / min–
GET /id/lookup?realm={{home.realm}}&handle=…Resolve a handle to an account id and its home120 / min–
GET /id/{account}/logThe newest log120 / min–
GET /id/{account}/publicThe signed public profile120 / min–
POST /id/registerRegister an identity with this home3 / hour–
POST /id/{account}/eventsNewer events (rotation, retirement)30 / hour–
POST /id/{account}/instanceMove here or reset (key tool)30 / hour–
GET /id/{account}/locksLock hints for sign-in30 / hour30 / hour
POST /id/{account}/challengeA single-use challenge (60 s)10 / min30 / hour
POST /id/{account}/fetchThe vault, after a lock proof30 / hour10 / hour
POST /id/{account}/loginSign in; returns a bearer token10 / min30 / hour
/session/*Vault, profile, password change, export, logout120 / min; password change 10 / hour–

IPv6 addresses are limited per /64. Only failed requests count against an identity, so requests anyone can make, such as reading the lock hints, cannot use up its owner's sign-in budget. Failed fetches, which are password guesses, still can: that is the trade-off HOST_PROTOCOL.md §6 describes.

Outside /v0, at the root of the origin, the host pointer GET {{home.url}}/.well-known/rootcard ([HST-23]) answers { "v": 1, "base": "{{home.url}}", "api": ["v0"] }, so clients given the bare domain resolve it with wellKnownBase. When the operator has named their account id, the origin also serves GET {{home.url}}/.well-known/rootcard-link: the operator's link token, so the operator's identity can list {{home.host}} as its website.

Errors are JSON objects with the specification's codes ({ "error": "not_home", … }). CORS is open and no endpoint uses cookies. Full details: HOST_PROTOCOL.md.
